# Phase 1 — Dataset Audit & Cleaning Log
mcPHASES · 2022 interval · logged 3–7 September 2026

## 1. File inventory (raw audit)

23 CSV files scanned. Row counts ranged from 42 (`subject-info.csv`, `height_and_weight.csv`) to 63.1M (`heart_rate.csv`). Full column/dtype/missingness listing generated by `audit_phase1.py`.

**Key finding:** `hormones_and_selfreport.csv` already merges self-reported symptoms + LH/estrogen/PdG + hormone-verified `phase` label in one table (5,659 rows, 42 participants). No separate hormone-join needed — reduces pipeline complexity.

## 2. Decision: exclude raw sub-daily wearable tables

**Observed:** `heart_rate.csv` (63.1M rows), `calories.csv` (20.2M), `distance.csv`/`steps.csv` (7.7M each), `wrist_temperature.csv` (6.9M), `estimated_oxygen_variation.csv` (3.1M), `altitude.csv`, `active_zone_minutes.csv` — all sub-daily raw sensor streams, not daily aggregates.

**Why excluded:** aggregating these to daily features would consume disproportionate engineering time for a 9-week solo project, and Fitbit already provides pre-aggregated daily-resolution tables for the same signal.

**Decision:** use pre-aggregated tables instead — `resting_heart_rate.csv` (13,737 rows), `sleep.csv` (14,765 rows), `computed_temperature.csv` (5,575 rows, nightly baseline-relative temperature). All three confirmed at 42/42 participant overlap with the hormone/symptom table, zero dropout.

## 3. Decision: restrict to 2022 interval only

**Observed** (splitting `hormones_and_selfreport.csv` by `study_interval`):
- 2022: symptom fields ~10.2% missing
- 2024: symptom fields ~99.4–100% missing
- `pdg` (progesterone): 100% missing in 2022 — it turns out `pdg` was only ever logged in the 2024 round, which is itself unusable

**Why:** 2024 self-report is not usable at any reasonable missingness threshold. Matches the pattern reported in the base paper (Specht et al. 2026), confirmed independently against this data pull rather than assumed.

**Decision:** all modeling restricted to **2022 interval only**. `pdg` dropped from the hormone feature set (orphaned in the unusable interval) — final hormone features are `lh` and `estrogen` only.

## 4. Bug found and fixed: cycle-onset detection

### 4a. First attempt — silently broken

Initial onset-detection code treated `flow_volume` as numeric (`flow_volume > 0`). Result: **0 detected cycle onsets across all 42 participants** — a diagnostic bug, not a real absence of periods in a menstrual-health cohort.

**Root cause:** `flow_volume` is a categorical text field (`"Not at all"`, `"Spotting / Very Light"`, `"Light"`, `"Somewhat Light"`, `"Moderate"`, `"Somewhat Heavy"`, `"Heavy"`, `"Very Heavy"`), not numeric. Comparing text against `0` fails silently rather than raising an error, masking the bug until output was inspected.

**Fix:** redefined bleeding as `flow_volume.notna() & (flow_volume != "Not at all")`.

### 4b. Second attempt — detection worked, but too noisy

After the type fix, onset detection ran, but produced clearly unrealistic results:
- 161 raw "cycle length" gaps, median 12 days, with 60+ instances of 2–5 day "cycles"
- Two participants (ids 40, 47) showed 19 onsets in a 90-day window

**Root cause, two compounding issues:**
1. **Spotting mis-flagged as new cycle starts.** A single "Spotting / Very Light" day occurring days after a real period was counted as an independent bleed onset.
2. **Missed-logging days fractured real periods.** A single `NaN` or "Not at all" day inside an actual multi-day bleed broke one real period into two false "episodes."

**Fix, two-part:**
- **Gap bridging:** within a bleeding streak, gaps of ≤2 days are bridged (treated as still part of the same episode) so a single missed-log day doesn't fracture a real period.
- **Short-interval merging:** any detected episode starting <15 days after the previous one is merged into it — no real menstrual cycle is that short, so this collapses spotting/noise into the adjacent real period.

### 4c. Result after fix — validated against known biology

- Median cycle length: **29 days**, mean **30.5**, IQR **27–33** — consistent with normal menstrual cycle length ranges, i.e. the detection logic now produces biologically plausible output rather than being merely "no longer zero."
- 10 residual outliers (17 days to 61 days) remain across the cohort of ~79 total detected cycles. These are treated as genuine participant-level cycle irregularity, not further cleaned — self-tracked cohorts are expected to contain some genuinely irregular cyclers, and this is documented as a real finding for the error-analysis phase (Phase 8) rather than scrubbed out.
- **39 of 42 participants have ≥2 detected cycles** in the 2022 interval (usable for within-person/personalization comparison). Participants 32, 38, and 49 have only 1 detected cycle each — excluded from personalization/within-person evaluation, retained only for population-level baseline training.

## 6. Why this matters for the write-up

This log is the evidentiary basis for the "Dataset" and "Data Processing" sections of the eventual paper, and for the Phase 1 (14 Sept) presentation's methodology slides. It demonstrates:
- decisions justified by actually-observed missingness/coverage numbers, not assumptions carried over from the base paper without verification
- a caught-and-fixed measurement bug (Section 4a), with the fix's validity confirmed against known biological ranges (Section 4c) rather than accepted on faith
- explicit, stated exclusions (raw wearable tables, 2024 interval, `pdg`, 3 single-cycle participants) with reasons, not silent scope-narrowing
